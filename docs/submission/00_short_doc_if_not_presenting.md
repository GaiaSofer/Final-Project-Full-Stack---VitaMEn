# מסמך קצר — במקום הצגה (לפי הודעת אוהד, 31.8, להגשה עד 16.9)

## 1. מה בניתי ואיך משתמשים בזה

בניתי את **VitaMEn** — אפליקציית מעקב תוספי תזונה. הבעיה: שוק תוספי התזונה
לא מפוקח, ואנשים שנוטלים כמה תוספים במקביל לא רואים שרכיב מסוים (ברזל,
אבץ, ויטמין D, קפאין) חוזר על עצמו בין המוצרים ומצטבר לחריגה ממינון בטוח.

שני סוגי משתמשים:
- **לקוח** — בונה "מחסנית" תוספים אישית, מקבל התרעה בשלושה מצבים (אדום =
  חריגה מהתקרה הבטוחה, צהוב = חפיפת רכיב בין מוצרים, ירוק = הגעה ליעד
  שרופא קבע), מסמן נטילה יומית, ומשווה מחירים בין מותגים כדי למצוא חלופה
  זולה יותר לאותו רכיב.
- **מנהל** — מתחזק את הקטלוג המשותף: מוסיף מוצרים (בודד או ייבוא CSV
  מרובה), עונה לבקשות מוצר מלקוחות, מנהל טיפים יומיים, ורואה יומן פעולות
  (מי הוסיף מה ומתי).

איך משתמשים (הרצה מקומית, פירוט מלא ב-`הרצה.md`): `npm install` →
מדביקים מפתח Supabase ב-`.env.local` → מריצים את קבצי ה-migrations לפי
סדר ב-Supabase SQL editor → `npm run dev`. נרשמים פעם כ-admin (רואים את
הקטלוג) ופעם כ-client (מוסיפים תוסף, רואים התרעה). `npm test` מריץ 35
בדיקות אוטומטיות.

## 2. מה היה קשה

הקושי המרכזי לא היה תיקון באג ספציפי, אלא ההתנעה עצמה — הפער בין "יש לי
רעיון למוצר" לבין "יש לי משהו שרץ בפועל". שלושה חסמים קונקרטיים בלטו
יותר מהשאר:

איך בכלל מתרגמים רעיון למערכת עובדת — לא רק לתכנן על הנייר, אלא להחליט
בפועל מאיפה מתחילים, מה כל שלב דורש בהמשך, ומה אפשר לדחות בלי לתקוע את
הכל. איך ממלאים קטלוג עם מוצרים אמיתיים ולא רק כמה שורות דוגמה — כדי
שהאפליקציה תרגיש כמו מוצר, לא כמו הדגמה עם שלושה פריטים. ואיך בונים
מנוע המלצות ("גאיגי") שעונה על שאלות מתוך הקטלוג בלי להזדקק למפתח API
חיצוני — כלומר לוגיקה מקומית שמריצה חיפוש והשוואה על הדאטה שכבר בקטלוג,
במקום לקרוא למודל שפה חיצוני שיכול פשוט להמציא תשובה.

שלושת אלה ביחד היו החלק הכי לא-ברור מראש בפרויקט — פחות "לתקן תקלה",
יותר "איך בכלל בונים את זה מהתחלה".
